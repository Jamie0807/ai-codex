# 调研工作流

## 1. 界定问题

先提取以下信息：
- 决策目标：需要选择或设计什么。
- 约束条件：技术栈、运行环境、规模、预算、团队能力、截止时间、兼容性。
- 成功标准：可靠性、速度、成本、开发体验、安全性、可维护性、用户体验。
- 排除项：用户已经明确不考虑的方案。

如果当前有相关代码仓库，先检查本地文件：包管理清单、配置、框架入口、已有工具函数、测试和文档。

## 2. 搜索策略

不要只用一个宽泛关键词。组合使用多种搜索形态：
- 官方文档：`<技术> official docs <能力>`
- GitHub 仓库：`<能力> <语言/框架> github`、`<库名> alternatives github`
- GitHub issue/discussion：`<库名> issue <风险>`、`<库名> performance issue`、`<库名> migration`
- Reddit/社区：`site:reddit.com <库名> production`、`site:reddit.com <问题> <框架>`
- 方案对比：`<方案 A> vs <方案 B> <年份>`

技术问题优先使用一手来源：官方文档、标准、仓库文档、release notes、RFC、issue tracker、benchmark 源代码。技术文章和 Reddit 主要用于发现风险和真实使用经验，不要作为唯一证据。

## 3. 证据质量检查

评估 GitHub 项目时，检查：
- 最近是否有 release 或 commit。
- open issue 数量与维护者响应是否匹配。
- 示例是否匹配用户技术栈。
- license 是否兼容。
- 在相关场景下是否有 TypeScript/types、测试、CI、文档。
- 是否有破坏性变更历史和迁移文档。

评估 Reddit/社区反馈时，检查：
- 帖子是否足够新，是否仍适用于当前技术版本。
- 抱怨是否描述了具体失败模式。
- 是否有多个独立用户报告类似问题。
- 是否有维护者或有经验用户进行纠正。

评估官方文档时，检查：
- 版本和日期。
- 兼容性说明。
- 价格、限制、安全和隐私约束。
- 是否存在明确废弃说明或官方推荐替代方案。

## 4. 构造候选方案

优先给出 3-5 个实现策略明显不同的方案。常见类型：
- 采用成熟库或服务。
- 采用更轻量、聚焦的库。
- 基于底层能力自研薄封装。
- 混合方案或渐进迁移路径。
- 暂缓或避免实现，因为复杂度大于收益。

不要加入明显不适合的方案。如果某个热门方案不符合用户约束，只有在解释“不推荐原因”有助于决策时才纳入。

## 5. 对比并推荐

根据用户标准评估每个方案。如果用户没有给出标准，默认使用：
- 正确性和可靠性。
- 与当前技术栈的匹配度。
- 维护健康度。
- 复杂度和集成成本。
- 运行时性能。
- 安全和隐私影响。
- 退出或迁移风险。

推荐结论必须明确：
- 点名默认推荐方案。
- 说明它为什么在当前约束下胜出。
- 说明什么情况下应该改选其他方案。
- 列出实施前需要验证的事项。

## 6. 风险表达

使用直接的风险分类：
- 技术风险：正确性、性能、兼容性、安全性。
- 产品风险：用户体验不匹配、功能缺口、流程摩擦。
- 运维风险：维护成本、故障处理、可观测性、支持能力。
- 迁移风险：数据模型变化、锁定、回滚成本。

区分已经确认的风险和仍需验证的不确定项。
