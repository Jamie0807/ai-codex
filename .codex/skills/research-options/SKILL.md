# 方案调研

## 目的

使用这个 skill 将开放式技术问题整理成可决策的候选方案。默认使用中文输出，提供 3-5 个经过调研的方案、证据链接、优势、风险点和推荐路径，并把完整调研结果写入一个 Markdown 文件，便于后续评审、归档和迭代。

## 默认流程

1. 只有在问题缺少目标、约束或成功标准时才追问。不要询问可以从仓库或网络资料中发现的事实。
2. 除非用户明确说不要联网，否则搜索最新资料。优先级为：官方文档/标准、活跃 GitHub 仓库与 issue/discussion、Reddit/社区反馈、技术文章。
3. 对比 3-5 个可行方案。不要为了凑数量加入明显无效的方案；如果真实可行方案少于 3 个，要说明原因。
4. 优先使用工程实践判断标准：成熟度、维护活跃度、集成匹配度、性能、安全性、开发体验、迁移成本和锁定风险。
5. 将完整方案写入文件。默认路径为 `docs/research/YYYY-MM-DD-topic-options.md`，其中 `topic` 使用用户问题的英文或拼音短 slug，例如 `large-file-upload`。如果用户指定了输出路径或文件名，优先使用用户指定值。
6. 最后在对话中给出明确推荐、文件路径和简短摘要；完整方案以文件为准。

当任务需要真实外部调研，或权衡点不简单时，读取 `references/research_workflow.md` 获取搜索模式和证据质量判断规则。

## 来源要求

- 使用联网搜索时必须提供来源链接。
- GitHub 的 star 只能作为弱信号；优先看近期提交、发布节奏、issue 质量、维护者响应、生态采用情况和示例质量。
- Reddit/社区反馈适合发现运维痛点、隐藏成本和失败模式，但只能作为方向性证据，不能单独作为权威结论。
- 官方文档是 API、限制、许可、兼容性和安全声明的事实来源。
- 如果资料互相冲突，要指出冲突，并给出明确判断。

## 文件生成要求

- 默认创建 `docs/research/` 目录；不要把完整调研只留在对话里。
- 文件名使用当前日期和主题 slug，例如 `2026-06-08-large-file-upload-options.md`。
- 文件内容必须包含完整证据链接、方案矩阵、推荐结论、风险验证清单和后续行动。
- 如果联网搜索过，文件中必须记录来源链接；对话最终回复也要给出关键来源或说明来源已写入文件。
- 如果由于权限、路径或用户明确要求导致无法写文件，要在对话中说明原因，并直接输出完整方案。
- 生成文件前检查目标目录，避免覆盖用户已有文件。若目标文件已存在，优先追加更具体的 slug 或时间后缀，例如 `-v2` 或 `-HHMM`。
- 方案文档是交付物；对话回复只做摘要，不重复粘贴完整文档。

## 方案文档格式

默认使用中文。除非用户指定其他格式，否则使用以下结构：

```markdown
# <主题> 方案调研

> 生成日期：YYYY-MM-DD
> 状态：调研建议 / 待验证 / 已采纳

**问题理解**
- 目标：...
- 关键约束：...
- 判断标准：...

**调研来源**
- 官方/标准：...
- GitHub：...
- Reddit/社区：...

**方案矩阵**
| 方案 | 核心思路 | 适用场景 | 优势 | 风险点 | 证据 |
|---|---|---|---|---|---|
| A | ... | ... | ... | ... | ... |

**推荐结论**
推荐：...
原因：...
不推荐/谨慎选择：...

**风险与验证**
- ...

**后续行动**
- ...

**参考链接**
- [来源名称](https://...)
```

矩阵要简洁。矩阵之后必须用文字解释推荐结论，让用户不用反复阅读每个单元格也能做决策。参考链接可以在正文中内联，也可以集中放在文末；使用联网搜索时至少保留关键官方文档或一手来源。

## 对话回复格式

文件生成后，对话中默认只返回：

```markdown
已生成方案文档：[文件名](/abs/path/docs/research/xxx.md)

推荐：...
关键原因：...
需要优先验证：...
```

如果用户明确要求“直接展示完整方案”，可以在写入文件后同时输出完整内容，但仍需提供文件路径。

## 不适用场景

不要将此 skill 用于没有调研或选型成分的纯实现任务、纯商业/运营/市场策略，或用户明确只需要单一已知答案且不需要备选方案的任务。
